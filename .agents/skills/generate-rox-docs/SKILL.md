# generate-rox-docs

A page is a JSON page model (`pages/<id>.json`) validated by `rox-dox check` and rendered by
`rox-dox build`. Every claim, node, edge, step, state, transition and relationship carries a
`source` at the pinned commit; the build refuses stale or missing citations. Author the model
with a script under `pages/authoring/` so it can be regenerated byte for byte.

## Procedure

1. Pin the commit. Every citation points at one rox-core SHA; read files with
   `git show <sha>:<path>`, never the working tree.
2. Read before writing: entry points, k8s/deploy config, models, the README of the folder.
   A claim you cannot cite is not written.
3. Fill sections in page order: Related, TLDR, block, schema, sequences, states.
   An empty section stays present and says so.
4. Sequences: invoke `minimal-cover`. One happy path per distinct execution mode the folder
   owns, not one per endpoint.
5. States: only entities with a persisted or enumerated state. States and transitions come
   from the code's enums and transition tables, not from reading the happy path.
6. Build, then look at the rendered page before reporting.

## Schema: tables and their implicit relationships

Schema diagrams show every table the page touches — no box limit — plus NoSQL stores
(Redis keys, DynamoDB/KV tables) the flows read or write.

rox-core mostly does **not** declare foreign keys: many are commented out
(`# ForeignKey("task_run.run_id")`) or omitted on purpose ("no foreign key to avoid locking the
organization row"). The extractor only sees declared `ForeignKey(...)`, so relationships must be
found and recorded in `data.relations`. A diagram with tables and no edges is incomplete.

For each pair of tables on the page, look for evidence, strongest first:

1. **Declared FK** — `ForeignKey("t.c")` in the column. Drawn automatically.
2. **ORM join** — `relationship(..., primaryjoin="foreign(A.x) == B.y")`.
3. **Query join or filter** — `.join(B, A.x == B.y)`, `.filter(A.x == B.y)`,
   `A.x.in_(select(B.y))`.
4. **Write site** — a row built with a value taken from another table:
   `TaskRunLog(run_id=task_run_id)`, `root_task_run_id = parent.root_task_run_id`.
5. **Lookup by id** — a function receives `x_id` and resolves it on one column:
   `Conversation.find_by_public_id(public_id=conversation_id)` proves `conversation_id`
   everywhere in that flow is `conversation.public_id`.
6. **NoSQL key** — a key builder or partition key embedding a SQL id:
   `f"chat:conversation:{conversation_id}:stream:{stream_id}"`, a DynamoDB partition key
   `conversation_id`. Pair it with (5) to name the SQL column.
7. **Hints only** — commented-out `ForeignKey`, `<table>_id` naming, a column comment
   ("stores a reference to the parent task run id"). A hint alone may be cited only when it is
   the column's own documented meaning; otherwise find (2)–(6).

`rox-dox relations --repo <rox-core> --commit <sha> --tables a,b,c` lists candidates from
signals 2, 3 and 7 with file and line. Confirm each candidate by reading the cited lines;
the tool proposes, the author decides.

Record each confirmed relationship as:

```json
{"src": "task_run_log.run_id", "dst": "task_run.run_id",
 "label": "written at queue time", "source": {"path": "...", "lines": [344, 351]}}
```

- `src`/`dst` are `table.column` for SQL; for a NoSQL store use the store `name`, optionally
  `name::field`.
- Cite the strongest evidence found; the `label` says what kind it is
  (`ORM primaryjoin`, `written at queue time`, `lookup by public_id`, `key embeds id`).
- Draw a relation only when both ends are on the page. Tenant columns (`rox_org_id`,
  `rox_user_id`) are drawn only if `organization`/`user` are on the page.
- Self-references (`parent_task_run_id → run_id`) are relations too.

## Checks before reporting

- `uv run rox-dox build pages --repo <rox-core> --repo-url https://github.com/Rox-AI/rox-core --out <dir>` succeeds.
- Every SQL table on the page has at least one relation, or the page says why it stands alone.
- Open the rendered page; every diagram is readable at full screen.
